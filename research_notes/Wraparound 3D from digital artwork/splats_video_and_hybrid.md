# Gaussian-splat, video-diffusion and hybrid routes to single-image wrap-around 3D (as of Nov 2026)

Scope: single-image to 360° asset for stylized/CG subjects (digital artwork, Blender renders), keeping the front-view fidelity that Apple's Spatial Scenes (`ImagePresentationComponent`, SHARP-family feed-forward splats) already give. Researched 2026-11-18. Items marked "(training knowledge, unverified this session)" come from the researcher's prior knowledge and were not re-checked against a primary source in this session. Treat them as leads.

## Which route gives the best visible-side fidelity plus a plausible back for stylized CG subjects?

### Takeaway
No single model does both. Feed-forward scene splat models (SHARP, Flash3D, Splatter Image-style) keep the front pixel-aligned but do not invent a back. Scene video-diffusion pipelines (Lyra 2.0, GEN3C, FlashWorld, Wonderland) are built for fly-throughs, not object orbits, and their licences mostly forbid commercial use. Object generators (TRELLIS.2, SAM 3D Objects, Hunyuan3D 2.x) give a full 360° object, but they regenerate the texture rather than copying the input pixels. The most promising route for a stylized character is therefore a hybrid: an object generator, or an orbit video model, for the geometry and the hidden sides, with the input image projected onto the visible side and blended at the seam. TRELLIS.2 (MIT) is the cleanest licence base for that.

### Cited Findings

**Feed-forward single-image gaussian models**
- Apple SHARP ("Sharp Monocular View Synthesis in Less Than a Second") regresses 3D Gaussian parameters from one photo in a single feed-forward pass, runs "in less than a second on a standard GPU", predicts on CPU/CUDA/MPS, and outputs `.ply` splats (OpenCV convention). It targets rendering of "nearby views"; the repo makes no 360° claim. Paper arXiv:2512.10685. — [apple/ml-sharp](https://github.com/apple/ml-sharp), [arXiv 2512.10685](https://arxiv.org/abs/2512.10685)
- Splatter Image (CVPR 2024) predicts one 3D Gaussian per input pixel with an image-to-image network. Because each Gaussian is tied to an input pixel, the input view is reproduced by construction. The network can still produce a 360° object reconstruction "by using the prior acquired during training", but only for categories it was trained on (it was trained on ShapeNet/CO3D-style object data). — [Splatter Image, CVPR 2024 paper](https://openaccess.thecvf.com/content/CVPR2024/papers/Szymanowicz_Splatter_Image_Ultra-Fast_Single-View_3D_Reconstruction_CVPR_2024_paper.pdf), [arXiv 2312.13150](https://arxiv.org/pdf/2312.13150)
- "Complete Gaussian Splats from a Single Image with Denoising Diffusion Models" (arXiv 2508.21542, 2025) uses a latent diffusion model to reconstruct a complete Gaussian-splat scene, occluded parts included, from one image at inference. It targets scenes rather than isolated objects. — [arXiv 2508.21542](https://arxiv.org/abs/2508.21542)
- LGM, GRM, GS-LRM and Long-LRM are multi-view-to-splat reconstructors. LGM and GRM reach a full 360° object from a single image only by first generating 4 or more views with a multi-view diffusion model (MVDream/ImageDream, Zero123++, Instant3D). GS-LRM and Long-LRM take posed multi-view input and are not single-image methods. Flash3D (2024) is a scene-level monocular-depth-based splat predictor and does not wrap around. LGM code is MIT. (training knowledge, unverified this session)

**Single-image object generators (full 360°)**
- TRELLIS.2 (Microsoft, 4B parameters, released Dec 2025) is an image-to-3D model. Model and code are MIT, though a dependency (nvdiffrast) has its own licence. Third-party sites say it outputs GLB with textures up to 4096² plus radiance-field and Gaussian outputs; the Gaussian output was not confirmed against Microsoft's own docs. — [microsoft/TRELLIS.2-4B model card](https://huggingface.co/microsoft/TRELLIS.2-4B/blob/main/README.md), [ComfyUI wiki news](https://comfyui-wiki.com/en/news/2025-12-18-microsoft-trellis2-3d-generation)
- One paper describes TRELLIS-style generation as starting from a Gaussian-noise-initialized geometry, so the texture is generated rather than projected from the input. — [arXiv 2505.21050](https://arxiv.org/pdf/2505.21050) (as summarized by search; partially verified)
- SAM 3D Objects (Meta, released 2025-11-19) "reconstructs full 3D shape geometry, texture, and layout from a single image", works on masked objects in cluttered scenes, and exports a Gaussian splat via `output["gs"].save_ply(...)`. Code and checkpoints are under the "SAM License" and access is gated on Hugging Face. The card does not say whether the output matches the input view, and it gives no hardware requirements. — [facebook/sam-3d-objects](https://huggingface.co/facebook/sam-3d-objects)
- An MLX port of SAM 3D Objects exists, so it may run on Apple silicon. — [appautomaton/sam-3d-objects-mlx](https://huggingface.co/appautomaton/sam-3d-objects-mlx) (existence only; quality not checked)
- Hunyuan3D 2.x generates the shape first, then paints it with Hunyuan3D-Paint. Paint takes normal and position maps of the generated mesh, generates multi-view images, and bakes them into a texture. It uses a delighting module and a reference-net so that the texture "should closely conform to the image prompt in the visible region". That is a design goal, not an exactness guarantee. — [Hunyuan3D 2.0 paper](https://arxiv.org/html/2501.12202v1), [Hunyuan3D 2.5](https://arxiv.org/pdf/2506.16504), [Hunyuan3D 2.1](https://arxiv.org/pdf/2506.15442)

**Video-diffusion / orbit pipelines**
- SV3D (Stability) takes a still image of an object and generates an orbital video of it, which makes it object-centric. — [stabilityai/sv3d card](https://huggingface.co/stabilityai/sv3d/blob/refs%2Fpr%2F29/README.md), [Stability generative-models repo](https://github.com/Stability-AI/generative-models)
- SV4D 2.0 takes a single-view video and generates novel-view videos: 48 frames (12 frames × 4 views) at 576×576, plus an 8-view variant. The repo lowers memory with `--encoding_t=1 --decoding_t=1` or `--img_size=512`, but gives no VRAM figures. — [Stability SV4D 2.0 announcement](https://stability.ai/news/stable-video-4d-20-new-upgrades-for-high-fidelity-novel-views-and-4d-generation-from-a-single-video), [stabilityai/sv4d2.0](https://huggingface.co/stabilityai/sv4d2.0)
- NVIDIA Lyra 2.0 (released 2026-04-14) generates "persistent, explorable 3D worlds" from one 480×832 image plus a camera trajectory (81 frames recommended). It is built on Wan2.1-14B, outputs a 3D Gaussian `.ply`, and runs on Linux with Ampere, Hopper or Blackwell GPUs (H100/GB200 targeted); the card gives no inference VRAM figure. It is described as scene-level, with no object-orbit mode. — [nvidia/Lyra-2.0](https://huggingface.co/nvidia/Lyra-2.0), [arXiv 2604.13036](https://arxiv.org/pdf/2604.13036)
- Lyra 1.0 (arXiv 2509.19296) self-distils a video diffusion model into 3D Gaussians. Its code is Apache-2.0 and its models are under the NVIDIA Open Model License. — [nvidia/Lyra README](https://huggingface.co/nvidia/Lyra/blob/main/README.md), [arXiv 2509.19296](https://arxiv.org/html/2509.19296v1)
- GEN3C (NVIDIA) builds a 3D cache of point clouds from predicted depth, renders it along a user-specified camera path and conditions a video model on those renders. From one image it generates 121 frames, and longer runs are autoregressive. The checkpoint is GEN3C-Cosmos-7B. It was tested only on H100/A100 and peaks at about 43 GB with full offloading. Code is Apache-2.0 and models are under the NVIDIA Open Model License. — [nv-tlabs/GEN3C](https://github.com/nv-tlabs/GEN3C)
- FlashWorld (arXiv 2510.13678, Oct 2025) makes 3D scenes from one image or a text prompt "within seconds", reportedly 10 to 100× faster than earlier work. Its 3D-oriented mode outputs 3DGS parameters directly, and it benchmarks against CAT3D, Bolt3D and Wonderland. — [FlashWorld](https://arxiv.deeppaper.ai/papers/2510.13678v1)
- Wonderland (Snap, CVPR 2025) predicts 3DGS feed-forward from video-diffusion latents, for scene navigation. — [arXiv 2412.12091](https://arxiv.org/abs/2412.12091v1), [Snap Research](https://research.snap.com/publications/wonderland-navigating-3d-scenes-from-a-single-image.html)
- CAT3D (Google) and ViewCrafter are multi-view or video novel-view generators followed by 3DGS optimisation. CAT3D's weights were never released. (training knowledge, unverified this session)

### Inferences
- For a stylized character or object, the object-centric generators (TRELLIS.2, SAM 3D Objects, Hunyuan3D, SV3D-then-reconstruct) are the right family for the back. The scene world-models (Lyra 2.0, GEN3C, FlashWorld, Wonderland) are tuned for camera fly-throughs of environments, and their orbit around a single subject will likely be weaker. The Lyra 2.0 card says so implicitly by describing scene-level output only.
- SHARP's front fidelity comes from pixel-aligned splats. Any 360° method that regenerates the texture (TRELLIS.2, Hunyuan-Paint, SAM 3D) will lose some of that fidelity on the front unless the input view is projected back onto it.
- Stylized and CG subjects suit object generators reasonably well, because those models are trained heavily on synthetic Objaverse-style CG assets. Photoreal-trained scene models (SHARP, Lyra) have no back-of-object prior for characters. This is an inference, not a measured result.
- The video-diffusion orbit routes need datacenter GPUs (14B Wan, about 43 GB GEN3C), which rules out on-device generation on Vision Pro. They are server-side only.

### Gaps
- I found no benchmark comparing front-view PSNR/LPIPS of TRELLIS.2, SAM 3D Objects or Hunyuan3D against the input image on stylized art.
- Runtime and VRAM figures were not found for TRELLIS.2, SAM 3D Objects, SV3D or FlashWorld in primary sources this session.
- Wan- or Hunyuan-Video camera-controlled object-orbit LoRAs (e.g. ReCamMaster, CameraCtrl II style) were not researched within the call budget.
- I did not find whether any 2026 feed-forward splat model produces full 360° objects from one image without a multi-view diffusion stage.

## Is there an off-the-shelf way to keep the input view pixel-exact on a 360° asset?

### Takeaway
No off-the-shelf tool found guarantees it. Hunyuan3D-Paint and similar texture painters aim to conform to the input in the visible region but do not promise exactness. Pixel-aligned splat predictors (Splatter Image, SHARP) reproduce the input view by construction but do not wrap convincingly. The practical answer is a custom composite: generate a 360° asset, then overwrite the front-visible texels or splats with the input image (back-projection with depth test), or keep the SHARP splats as the front shell and fill only the occluded region with generated splats. Seam blending is then needed.

### Cited Findings
- Hunyuan3D-Paint's stated goal is that the texture "should closely conform to the image prompt in the visible region", via a delighting module plus a double-stream reference-net. That is soft conditioning, not projection, and the delighting step deliberately changes the input's shading. — [Hunyuan3D 2.0 paper](https://arxiv.org/pdf/2501.12202)
- A community Hunyuan3D wrapper describes projecting each view onto the surfaces its camera sees, with depth testing and blending where views overlap, while diffusion stays conditioned on the front. Side pictures are dropped without warning when the projection option is off. This is a third-party implementation note. — [HartsyInference PR #933](https://github.com/HartsyAI/HartsyInference/pull/933)
- A review notes that multi-view-then-reproject texturing methods (MV-Adapter among them) "suffer from inconsistencies and occlusion blind spots due to direct projection". — [MV2UV notes, CVPR 2026](https://github.com/zhaoyang97/Paper-Notes-en/blob/main/docs/CVPR2026/3d_vision/mv2uv_generating_high-quality_uv_texture_maps_with_multiview_prompts.md)
- A paper reports that baking can misalign pixels when generated frames are reprojected onto the mesh using camera parameters, so back-projection has its own accuracy limits. — [arXiv 2505.21050](https://arxiv.org/pdf/2505.21050) (via search summary)
- Ink3D (arXiv 2607.01222, ECCV 2026) splits geometry from texture. An off-the-shelf generator makes a white mesh, "OrbitPainter" (a conditional video model) renders dense orbit-scan videos, and "TextureOptimizer" neural-bakes them while mitigating geometry inconsistency. It claims more faithful reproduction of "intricate textures from reference images" than prior work, but makes no exactness claim and states no code or licence on the abstract page. It is the closest 2026 match to a video-orbit-to-texture hybrid. — [arXiv 2607.01222](https://arxiv.org/abs/2607.01222), [project page](https://yuehan99.github.io/Ink3D-TextureGen/)
- Inpaint360GS (WACV 2026) does object-aware 3D inpainting in 360° gaussian scenes. It is relevant as a splat-completion technique, though it needs multi-view captures. — [Inpaint360GS](https://arxiv.org/pdf/2511.06457)
- "3D Gaussian Splatting Texture Editing via Single Modified Image" (IEEE TVCG 2026) propagates a single edited view's texture onto an existing 3DGS while keeping multi-view coherence. It could serve to stamp the exact input view onto a generated 360° splat. — [doi 10.1109/tvcg.2026.3684949](https://doi.org/10.1109/tvcg.2026.3684949)
- Splatter Image's per-pixel Gaussians make the input view reconstructable by construction. — [arXiv 2312.13150](https://arxiv.org/pdf/2312.13150)

### Inferences
- A feasible exact-front pipeline (my design, not a published tool):
  1. Generate a 360° object with TRELLIS.2 (MIT) or SAM 3D Objects, as splats or a mesh.
  2. Register it to the input camera, by estimating the generator's canonical front pose and refining it by silhouette alignment.
  3. Either (a) mesh: project the input image onto front-facing, depth-test-visible texels and feather by the view-angle cosine near grazing angles; or (b) splats: replace generated splats in the front-visible frustum with SHARP's pixel-aligned splats, or fine-tune the generated splats with a photometric loss on the input view only, plus a regulariser that keeps the generated back fixed.
  4. Blend the seam where surface normals approach 90° to the input camera.

  For CG renders with flat or known lighting, skip delighting so the input colours carry through unchanged.
- An exact front is easiest with splats. A splat optimisation step that holds the input view as a hard photometric target (the classic 3DGS loss on one view) naturally reproduces it, while the generated orbit views supervise the rest at lower weight. This is standard 3DGS training with weighted views, not a novel method.
- Stylized art often has outlines, cel shading and painted highlights that a delighting module would strip. Keeping the input's shading on the front, while generated sides are shaded differently, will make the seam visible. Seam blending matters more for this content than for photos.

### Gaps
- No paper or tool was found that explicitly guarantees exact input-view reproduction on a generated 360° asset. Unique3D's ISOMER and MV-Adapter's texture pipeline were searched, but no primary source on input-view colour projection was retrieved.
- Ink3D's code and licence availability are unknown.
- TEXGen and Paint3D were not checked in this session.

## Runtime/VRAM and licences (commercial use; user is in the EU)

### Takeaway
Licences decide this. SHARP's weights are research-only, Lyra 2.0 is research-only, and Hunyuan3D's licence excludes the EU entirely. TRELLIS.2 (MIT) is the clearest commercial-safe generator. SAM 3D Objects (SAM License), GEN3C and Lyra 1 (NVIDIA Open Model License) and SV3D/SV4D (Stability Community License, under US$1M revenue) are possible but need their licence text read. On the Apple side, RealityKit 27 now renders splats natively.

### Cited Findings

Derivatives are "limited to Research Purposes as well". - **Lyra 2.0 weights:** Under the "NVIDIA Internal Scientific Research and Development Model License". Commercial use, production use, distribution and sublicensing are not permitted. - **GEN3C:** Code is Apache-2.0 and models are under the NVIDIA Open Model License; custom licences go through NVIDIA Research Licensing. — [nv-tlabs/GEN3C](https://github.com/nv-tlabs/GEN3C)
- **Hunyuan3D 2.0/2.1:** "Territory" means "the worldwide territory, excluding the territory of the European Union, United Kingdom and South Korea", so an EU user has no licence without Tencent's written approval. — [Hunyuan3D-2 LICENSE](https://huggingface.co/tencent/Hunyuan3D-2/blob/main/LICENSE), [scancode licensedb](https://scancode-licensedb.aboutcode.org/tencent-hunyuan-3d-2.0-cla.html)

- **NVIDIA Open Model License:** It permits commercial use of models and outputs. (training knowledge, unverified this session)

**Runtime/VRAM**
- SHARP runs in under 1 s on a standard GPU and also runs on MPS (Apple silicon). — [apple/ml-sharp](https://github.com/apple/ml-sharp)
- GEN3C peaks at about 43 GB with full offloading and was tested on H100/A100 only. — [nv-tlabs/GEN3C](https://github.com/nv-tlabs/GEN3C)
- Lyra 2.0 is 14B-parameter Wan2.1 on Ampere/Hopper/Blackwell under Linux, with no VRAM figure given. — [nvidia/Lyra-2.0](https://huggingface.co/nvidia/Lyra-2.0)
- FlashWorld generates in seconds, reportedly 10 to 100× faster than earlier work. — [FlashWorld](https://arxiv.deeppaper.ai/papers/2510.13678v1)

**Rendering on Apple Vision Pro**
- RealityKit 27 (WWDC26) adds native Gaussian splat rendering: `GaussianSplatResource.BufferResource(count:position:scale:rotation:opacity:sphericalHarmonics:)` goes into a `GaussianSplatResource`, which goes into a `GaussianSplatComponent` on an entity. The API "does not assume a specific file format", so apps supply position, scale, rotation, opacity and SH buffers. — [WWDC26 session 279](https://developer.apple.com/videos/play/wwdc2026/279/)
- Availability is visionOS, iOS, iPadOS and macOS 27.0+ (Xcode 27). Splats do not render in Simulator. RealityKit can apply exponential/sigmoid activations so standard 3DGS PLY fields load directly. SH degree is 0 to 3 (`f_rest` 0/9/24/45 floats). Rotation is w,x,y,z. Non-finite values are rejected. Scene lighting does not affect splats, and they cast no shadow beyond the optional `GroundingShadowComponent` proxy. The sample loads from USD (`ParticleField3DGaussianSplat` prim via USDKit) or PLY. — [Apple: Rendering Gaussian splats with RealityKit](https://developer.apple.com/documentation/visionos/rendering-gaussian-splats-with-realitykit.md)
- Splat budget: "A scene can only render a limited number of splat entities at once". When an asset costs too much, RealityKit itself reduces splat rendering quality and sends `GaussianSplatEvents.RenderingChanged` (`isRenderingLimited`, `renderingStatus`). "Reducing the asset's splat count … brings back full-quality rendering." No numeric limit is published. — [Apple sample doc](https://developer.apple.com/documentation/visionos/rendering-gaussian-splats-with-realitykit.md); a secondary source says the `BufferResource` initializer throws above an internal cap and that Apple7+ GPUs are required — [radiancefields.com Apple](https://radiancefields.com/platforms/apple)
- OpenUSD 26.03 (March 2026) shipped the `UsdVolParticleField` schema family, with `UsdVolParticleField3DGaussianSplat`, co-developed by NVIDIA, Adobe and Pixar. Apple presented it in WWDC26 session 285, alongside USDKit (Swift USD). Splats can therefore live inside USDZ/USD. — [radiancefields.com Apple](https://radiancefields.com/platforms/apple)
- The page names no link between RealityKit's new splat API and Spatial Scenes/`ImagePresentationComponent`. — [radiancefields.com Apple](https://radiancefields.com/platforms/apple)
- MetalSplatter (scier) renders 3DGS with Metal on iOS, macOS and visionOS, in stereo on Vision Pro via vertex amplification. v1.0 (Feb 2026) added native SPZ read/write and loads PLY. A fork (lanxinger) lists SOGS v2 `.sog` support, not confirmed upstream, and notes Debug builds run more than 10× slower than Release. An "~8M splat capacity" figure appears only on third-party skill pages and is unverified. — [scier/MetalSplatter](https://github.com/scier/MetalSplatter), [MetalSplatter 1.0](https://radiancefields.com/metalsplatter-releases-v1.0), [lanxinger fork](https://github-users.yhajoa.workers.dev/lanxinger/MetalSplatter)

### Inferences
- For the user's EU, potentially paid app (Convolution), viable generator bases are TRELLIS.2 (MIT), then SAM 3D Objects, GEN3C/Lyra 1 and SV3D after licence review. Hunyuan3D is out for an EU user, and SHARP weights and Lyra 2.0 are out for any commercial product. The app's existing use of Apple's in-OS Spatial Scenes is a different matter: it is an OS API, not the SHARP weights.
- Display: with visionOS 27, a generated 360° splat can be shown in RealityKit via `GaussianSplatComponent` without MetalSplatter, and mixed with mesh content in the same scene. On visionOS 26 MetalSplatter (Compositor Services/Metal) is the route. A 360° object typically needs far fewer splats than a scene, roughly a few hundred thousand, and should sit comfortably inside RealityKit's budget; that is unmeasured, so watch `RenderingChanged`.
- Mesh (USDZ) versus splat: a mesh with a projected input texture is easiest to make pixel-exact on the front and is lit by scene lighting. A splat keeps the soft, view-dependent look of SHARP output but ignores scene lighting, so a stylized character will look "baked". For CG art with baked shading, splats' unlit behaviour is arguably a feature.

### Gaps
- No published RealityKit or MetalSplatter splat count that sustains 90 Hz on Vision Pro was found.
- The SHARP code `LICENSE` terms (separate from the model licence) were not read.
- The SAM License's exact commercial terms and the NVIDIA Open Model License's terms were not read from primary text this session.
- Whether RealityKit 27 exposes Spatial Scenes' generated splats as a `GaussianSplatResource` (which would allow editing or completing them) is unknown.
