# Hypnos: YouTube (sideload builds only, `HYPNOS_YOUTUBE`)

Moved out of `CLAUDE.md`. The build rule (compile all four platforms with and without the flag) stayed there.

**Nothing YouTube compiles unless `YOUTUBE_CONDITION=HYPNOS_YOUTUBE` is set** (`Configuration/Hypnos.xcconfig`; `build-and-sign --set YOUTUBE_CONDITION=HYPNOS_YOUTUBE`, or `EXTRA_BUILD_SETTINGS` in the gitignored `scripts/build-signing.conf`). Other visionOS YouTube players were pulled from the App Store, so until that is settled no YouTube code may reach a submission build. Every file is whole-file gated, and the shared code it touches (tab enums, settings, `MediaSegmentSkipper`, `VideoWindowModel`, `KeychainStore`, `AppLogger`) has `#if HYPNOS_YOUTUBE` cases. **Build all four platforms both with and without the flag before committing.** YouTube lives only in this app: Raven's Native Player and web-yt-dlp's own Apple apps were removed for it (2026-10-09).

The resolver chain (`Services/YouTube/YouTubeResolver.swift`), first match wins:
1. **On the device**: `YouTubeInnertube.player` asks YouTube's player API as its visionOS client (yt-dlp's `visionos` values plus a visitor id scraped from one watch page). The answer is an HLS master up to 2160p60 VP9 HDR, with no PO token and no player JS. Our own `AVPlayer` decodes it once `HypnosApp.init` registers the supplemental VP9/AV1 decoders, so the frames reach the depth pipeline. There are no ads: those are separate entries in the response, which nothing plays. Its audio is stereo AAC only. Made-for-kids videos and live streams come back unplayable.
2. **The optional backend** (`YouTubeBackend`, web-yt-dlp, `~/Projects/web-yt-dlp`): `/stream?transcode=never&height=1080` for what the device client refuses.
3. Otherwise the player API's reason, shown in an alert.

**Surround** is something not even YouTube's own apps offer. YouTube lists its 5.1 EC-3/AC-3 tracks only to a signed-in web client, which the backend is, because it holds the cookies; the device client never sees them (measured: no >2-channel format in 39 search results). `GET {backend}/api/youtube/audio?id=` returns the track as an audio-only HLS playlist. YouTube's master already keeps audio in separate `EXT-X-MEDIA` renditions, so `YouTubeManifestComposer` adds that playlist as one more audio group and moves every video variant onto it (stereo variants are dropped, so AVPlayer can't quietly pick stereo). The video stays YouTube's own. The composed master is served from `LoopbackPlaylistServer` (127.0.0.1, NWListener), because AVFoundation won't play a master from `file:`/`data:`, and a resource-loader scheme would have to be attached wherever an `AVURLAsset` is made, RAVEMedia's stereo engine included. If the spliced master doesn't decode (probe) or the native player fails, `VideoWindowModel+YouTube.dropYouTubeSurround` reopens the video with stereo at the playhead instead of falling back to WebKit.

- **Nothing reaches YouTube or SponsorBlock before a one-time approval** (decided 2026-10-20, like the old demo image source's "Load Sample Images?" wall, but kept). `YouTubeConsent` (`youtube.consentGranted` in UserDefaults) is set only by the tab's `YouTubeConsentWall`. There is no off switch (the user, 2026-10-20: leaving the tab alone is enough), and the YouTube settings stay hidden until then. The services check it themselves too, not only the UI: `YouTubeInnertube` (every call), `YouTubePageSession`/`YouTubeBrowserPage` loads, `SponsorBlock.segments`, and `YouTubeResolver.resolve` (so a shared `hypnos://play` YouTube link or a restored window can't reach out either). The user's own web-yt-dlp backend is not gated. New YouTube network code must check it too.
- **Identity** is `youtube:<id>` (`YouTubeVideoID.videoIdentity`), so depth caches and restoration key on the video. YouTube URLs expire after ~6 h and loopback URLs die with the process. `start()` therefore calls `refreshYouTubeStreamIfNeeded` before the renderer probe, so a stale URL never reaches it (the probe would route it to WebKit).
- **Picture quality** (`YouTubeQuality`: Auto, 2160p, 1440p, 1080p, 720p, 480p; saved as `youtube.quality`, chosen in YouTube settings or the video window's Quality menu). YouTube's master offers every rendition and the player picks by bandwidth, so a level is a cap on the player item (`preferredMaximumResolution`, applied by every player through `VideoWindowModel.maximumPictureResolution`; tvOS and macOS apply the saved level). The cap is a square as wide as a 16:9 picture of that height, so a portrait video of the same level fits under it. **The player keeps what it has buffered (a minute or more) at the old size**: lowering the cap also seeks to the playhead, after which the new size shows within about a second (measured on Apple's HLS sample; without the seek it took ~50 s). Auto leaves it to the player until 3D can't keep up (see 3D overload).
- **SponsorBlock** (`SponsorBlock.swift`, hash-prefix API) segments become `LibraryMediaSegment`s, so all three players (video window, tvOS, macOS) show them with the existing skip button via `MediaSegmentSkipper.load(videoIdentity:)`. Categories set to auto-skip (Sponsor, by default) skip by themselves, once each, in the video window only (`autoSkipYouTubeSegmentIfNeeded`, announced in the quality-notice slot). YouTube videos don't loop (`loopsAtEnd`).
- **UI**: `Views/YouTube/YouTubeTabView.swift` (public web search with continuation paging, paste a link, the signed-in feeds below, on-device history in `YouTubeHistory`) on every platform's tab bar. It resolves first, then opens the platform's player (`video-detail` window on visionOS/iOS/macOS, `TVVideoPlayerView` on tvOS). `YouTubeSettingsSection` (account sign-in/out, backend endpoint, token in the keychain, surround toggle, per-category SponsorBlock mode) is in all three Settings screens.
- **Signed-in feeds** (Home, Subscriptions, Watch Later, History; decided 2026-10-16, ported from web-yt-dlp's deleted player at `5aae2c7^`). They are **YouTube's mobile site itself**, in a hidden web view, read by a script: no API call carries the account, so its traffic is what a phone's Safari sends. Never "improve" this into `browse` calls with copied cookies.
  - `YouTubeAccount`: the session lives only in a web engine's cookies, a dedicated `WKWebsiteDataStore(forIdentifier:)` (tvOS: `HTTPCookieStorage.shared`, which `UIWebView` uses). Sign-in is Google's page in `YouTubeBrowserView`; passkeys don't work in an app's web view ("Try another way"). Each device signs in for itself: two live copies of one session can sign each other out. Playback stays signed out.
  - `YouTubePageSession` + `YouTubePageScript`: m.youtube.com at a phone's size (iPhone Safari UA), kept in the window by `YouTubePageHost` inside a zero-size clipping container. WebKit only checks that the view is in a visible window. Cards come from each card's `/watch?v=` link; byline is [channel, views, age]. **Load more** scrolls the last `ytm-continuation-item-renderer` into view; the page scrolls `body`, so `window.scrollTo` does nothing. An open dialog (the EU cookie consent) fixes `body`, so the model reports `.needsAnswer` and the browser opens the page for the person to answer.
  - **Nothing may play in the hidden page**: the mobile site autoplays a muted preview of the top card, which can count as a view. `evaluateJavaScript` counts as a tap and unlocks it (measured on macOS), so the app's calls use the SPI `_evaluateJavaScriptWithoutUserGesture:completionHandler:`, and the reader (in the `.defaultClient` content world, invisible to the page) pauses anything that starts.
  - **tvOS** uses the private `UIWebView` (by class name, as tvOS-Browser does), with a 0.5 s poll instead of a message handler. Every `stringByEvaluatingJavaScript` counts as a tap, and HTML5 video crashes it, so `play()` must refuse **before** the page's scripts run. An `NSObject` category method `webView:didCreateJavaScriptContext:forFrame:`, which WebKitLegacy calls as each window is created, installs `legacyDocumentStart`. That script also replaces `IntersectionObserver`: tvOS `UIWebView`'s own one never reports anything coming into view, so without it nothing ever loads more (all measured in the tvOS 26 simulator). Signing in on the TV uses `TVWebCursor`, a Siri Remote pointer.
  - **Tiles** show title, views, channel and the day it was published, one line each. Feeds and search only say "3 days ago", so `YouTubeUploadDates` asks `YouTubeInnertube.publishDate` (a signed-out WEB-client `player` call: no PO token, so it won't play, but its `microformat` has `publishDate`, ~3 KB; the visionOS client's answer has no dates) for tiles on screen only, two at a time, pausing 5 min if YouTube refuses one. Cached in Caches. The day is in the device's time zone, as the user's old userscript (greasyfork 493024, same request) showed it.
  - **Watch history** (decided 2026-10-18): what was watched and where each video was left lives on the YouTube backend (web-yt-dlp `/api/history`, SQLite), **never reported to YouTube** (the user clears YouTube's history often; reporting to YouTube was rejected as distinguishable or costly). `YouTubeWatchHistory` + `YouTubeWatchReporter`: each player (video window, `TVVideoPlayerView`'s `onProgress`, Mac `AVPlayerView`) reports start / every 10 s / pause / close with the time seen, through an outbox persisted in UserDefaults. Opening a video resumes at the saved position (≥ 15 s, not within 10 s of the end), asked from the server so another device's progress counts. Tiles draw a red bar from it (or YouTube's own bar on a signed-in page, read by the page script as `progress`). The Recently Watched shelf becomes "Watched", the server's list for all devices. **YouTube's history page is only read**: shown as the History shelf, or loaded once a day in a second hidden page, and posted to `/import` (adds what YouTube's apps watched; never moves a position back; removed videos stay removed). The Firefox extension in web-yt-dlp's `extension/` uses the same API. Off without a configured backend + token. The red-bar selector is unverified signed in.
  - **Working on the Vision Pro, signed in** (the user, 2026-10-16, build `f27e3ba`): sign-in, the hidden page and the signed-in feeds. Not yet checked: tvOS and the TV cursor's typing into Google's form, iOS and macOS sign-in.
- The player API and search are YouTube's private API: every parse is defensive. When it breaks, compare with yt-dlp's `extractor/youtube/_base.py` (`INNERTUBE_CLIENTS`). The visionOS values there were current on 2026-10-09.
