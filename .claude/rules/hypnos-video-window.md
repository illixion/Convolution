# Hypnos: video window, flat players and stereo/immersive playback

Moved out of `CLAUDE.md`. The fake-3D / depth pipeline is in `hypnos-ai-3d-video.md`; Jellyfin/Library streaming is in `hypnos-library-jellyfin.md`.

- **VideoWindowModel** - Per-window `@MainActor @Observable` model (mirrors `PhotoWindowModel`) owning the window's current video, navigation snapshot (own copy of `galleryVideos` + `currentIndex` + lazy pagination), 3D intent (`stereoscopicOverride`/`video3DSettings`), flip, per-window `currentAdjustments`, playback state (`currentTime`/`duration`/`isPaused`/`isMuted`/`bufferedEnd`/`isScrubbing`), the `VideoLoopController`, share state, and auto-hide timers. Side-effect-free `init`; side effects in `start()`; `cleanup()` on dismiss. This replaced the old shared `AppModel.selectedVideo`/`videoStereoscopicOverride`/`video3DSettings`/`isVideoFlipped`/`videoVisualAdjustments` + app-level auto-hide, so multiple video windows are fully independent (fixes the bug where every pushed window showed the last-selected video). Created with `@State` in `VideoWindowView(windowValue:appModel:)`.

- **VideoWindowView** - Thin wrapper handling both pushed and standalone modes via `wasPushed` (same pattern as `PhotoWindowView`). Picks the render path per `windowModel`: immersive `StereoscopicVideoView` (`shouldUse3DMode`), real-time `Pseudo3DVideoPlayerView` (`shouldUsePseudo3D`), else the flat player (`playbackRenderer`: `.resolving` → `.nativeMetal` `NativeMetalVideoPlayerView` → `.webKit` `WebVideoPlayerView`). Hosts one `RAVEPlayerControls` ornament for both 2D and fake-3D, with app actions supplied by `VideoOrnamentsView`. Locks window aspect ratio using **this** window's scene via `@Environment(SceneDelegate.self)` (not an arbitrary foreground scene); after each lock request a one-shot follow-up (`aspectRelockTask`) reads back the *granted* scene size and re-locks to a video-true size fitting inside it — portrait videos hit the platform's max window height, and a clamped grant under `.uniform` otherwise locks a wrong ratio (permanent letterbox between video and chrome, no room to enlarge). **Fake-3D chrome depth:** the ornament is kept coplanar with the visionOS window controls (`pseudo3DChromeZOffset = 0`; an earlier 20cm push floated the chrome off that plane and occluded the window controls) and the video is pulled back to that same plane by `Pseudo3DVideoPlayerView.videoPlaneZRecess` (90pt ≈ 9cm; the front-aligned `.frame(depth: 0, alignment: .front)` slab sits at the front of the window's depth region, measured ~9cm proud of the chrome on-device — the recess is applied as `.offset(z:)` on the GeometryReader3D so the fit math is unaffected; both constants stay tunable). `pseudo3DChromeBottomLift`/`ornamentBottomPadding` reserve the shared controls' footprint and keep it clear of the video and system window controls.

- **VideoControlBar** - Thin adapter from `VideoWindowModel` command closures to RAVEUI's `RAVEPlayerControls` in its `.strip` layout (every platform the window runs on): native SwiftUI scrubber, previous/next video around ±10s and play/pause (`RAVEPlayerNavigation`, when the window browses a list), volume, buffering, A/B markers, the skippable segments marked under the track (`MediaSegmentSkipper.markedRanges`) and the picture readout (`VideoWindowModel.pictureDetails`). WebKit, Metal and stereo all drive the same UI through the active renderer's closures. A drag seeks once on release; scrub/scroll lifecycles suspend auto-hide. On visionOS the strip is as wide as the window (`VideoWindowView.stripWidth`, 760…1180 pt).
- **Picture readout** ("1920×1080 · 23.976 fps"): `pictureSize` / `pictureFrameRate` on the model, written only on a change, cleared per video. The size comes from every renderer's `onVideoSizeKnown` (and the WebKit page's state reports, so an adaptive stream's new size shows); the rate from the native player's track (`nominalFrameRate`, else `currentVideoFrameRate` at 1×, polled every 2 s for HLS variant changes), the WebKit page's `requestVideoFrameCallback` media times (median gap over ~90 frames after each load and seek), or the stereo pump's `sourceFramesPerSecond`. Rates are snapped to the standard ones (`VideoPictureFormat`).

- **VideoOrnamentsView** - The window's feature buttons on the strip, by priority (`PlayerAccessoryLayout` hands each side the room): 0 View Mode and Quality (badges), 1 Subtitles, Speed and the conversion status, 2 A-B loop and Info (Stash), 3 Share and Gallery; then the pinned Cinema button and More. More holds what the strip had no room for and what is only ever there (flip, convergence and subtitle timing rows, All Adjustments, Slideshow, Pop Out, Open in Safari). The immersive path keeps a plain bar of the same buttons with prev/next and a More Options Menu. The title is the window's own (below). The ViewMode menu switches **2D**, immersive **3D** (+ "Edit 3D Settings" when active), and **"AI 3D"** (formerly "Convert to 3D (Beta)"; named apart from "3D" so it reads as depth estimated from a 2D picture, not a 3D movie) — the fake-3D path (gated `disabled` to `windowModel.pseudo3DAvailable` — AVFoundation-decodable now, or reachable via the Stash transcode; realtime or pre-processed, see the engage flow below). The three modes are a **radio group** (`modeButton` + `currentViewMode`): exactly one carries the checkmark, selecting another switches directly, re-selecting the active one is a no-op (leaving a mode = picking another). There is no "3D Depth" preset submenu (strength is pinned — see `Pseudo3DSettings`; convergence lives in the Adjustments window); whenever fake-3D is available (`pseudo3DAvailable`) the menu also shows **both** depth-model submenus — **Depth Model (Real-Time)** and **Depth Model (Pre-Process)** — and this video's conversion progress + Cancel while a background conversion runs; the mode label reads `3D*` in fake-3D. Playback transport and feature actions share one `RAVEPlayerControls` ornament in both 2D and fake-3D. The immersive scene owns its own transport. The More menu's **Adjustments** button opens the standalone `video-adjustments` window (`VideoAdjustmentsWindowView`) rather than a popover — it sets `appModel.videoAdjustmentsTarget`, so the panel is freely repositionable and never occluded by the front-plane fake-3D video; also Slideshow and Pop Out (when pushed). Info button opens `MediaDetailSheet`. Takes `@Bindable var windowModel`.

- **Title and details** - `PlayerTitleButton` (`Views/Videos/PlayerDetails.swift`) names what plays in the top-left corner, with the chrome: on visionOS an ornament at `.scene(.topLeading)` over the window's corner (SwiftUI can't draw over a stereo picture), on iOS beside the close button. An episode reads as its series over "S1 E3 · Title". A tap opens the details in a popover ("Details", one of `popoverMenuNames`, so a tap on the picture closes it): a Library title's series, episode, year, runtime, ratings, genres and overview from `LibraryService`, a Stash scene's studio, date, performers, tags and description from `fetchSceneDetail`, otherwise the file and its picture (`PlayerDetails(video:)`, shown until the server answers). The film player has the same corner (visionOS, iOS, and a focusable corner button with a details sheet on tvOS); tvOS's video player hands the same details to AVKit's own Info panel instead (see the tvOS rule).
- **Next episode carries on** (`VideoWindowModel.EpisodeCarryOver`): an episode that autoplays the next one hands it AI 3D (real-time, or the next episode's conversion when it has one; not while the window holds the Big Screen), the stream level Auto had settled on (the 1080p AI 3D starts at, or a step down for a stalling connection; fetched with `streamPlan(quality:forAI3D:)` before the switch, so the next episode doesn't start high and step again), and "already told 3D can't keep up". A video picked by hand starts afresh, as before.
- **Playback speed** - `PlaybackSpeedMenu` (`PlayerQuickControls.swift`, 0.5–2×, its badge filled when not 1×) sits with the Playback choices on the bar and in More, in the video window and the film player. `VideoWindowModel.playbackSpeed` is per window: kept through every renderer change and the next video, never restored with the window. Renderers take it like the volume: read at load (`defaultRate` on each `AVPlayer`, so every `play()`, loop and involuntary resume keeps it; `defaultPlaybackRate` in the WebKit page, which a source swap resets to) and live through `setSpeedCommand`; the immersive player reads its owner's. The Cinema screen shows the window's own player, so it follows. Above 1× real-time AI 3D shows no more frames a second than the video has at 1× (Vergence's `StereoPump` frame cap), and the pump's keeping-up report counts against that rate, so the 3D overload step-down works at any speed. tvOS and the Mac video window are AVKit's players, whose own speed menu is left on.

- **VideoLoopController** - `@Observable @MainActor` per-window model (owned by `VideoWindowModel`) for the A-B loop on the 2D web player. Cycles `idle → aSet → active → idle`: 1st press sets A, **2nd press sets B and engages immediately** (no confirmation step), 3rd press (or the control-bar clear button → `clear()`) disables. Owns its own toast state. Wires `queryCurrentTime`/`setLoopBounds` closures bound by `WebVideoPlayerView` to the JS rVFC monitor (`window.__startABLoop` / `window.__stopABLoop`).

- **Stream-URL strategy (Stash scenes)** - `GalleryVideo.streamURL` is **always the server's original file**; `transcodeStreamURL` holds Stash's live transcode (HLS `/stream.m3u8` preferred, else the non-seekable fragmented `/stream.mp4`) as a *reserve*, populated for every scene advertising endpoints when Settings → Server-Side Transcoding is on (`enableStashTranscoding`, default on). WebKit decodes WebM (VP8/VP9) on-device, so nothing transcodes up front. The transcode is engaged in exactly three cases: (1) the WebKit player reports the original unplayable — a decode/unsupported-source error immediately, a network error after its retries — via `onSourceUnplayable` → `VideoWindowModel.handleSourceUnplayable()`; (2) any fake-3D engage on a WebKit-decoded source, funnelled through `enablePseudo3D()`; (3) `transcodedDownloadURL` (MV-HEVC + depth pre-process), which prefers the transcode rewritten to `/stream.mp4` because AVAssetReader can't read WebM at all. `VideoWindowModel.activeStreamURL`/`usingTranscodedStream` track which one is playing (reset per video switch); `canUseTranscodedStream` and `pseudo3DAvailable` gate the UI. **AVFoundation still cannot decode WebM on visionOS 27** (VP8 and VP9 both fail `AVURLAsset.isPlayable`), which is why the transcode detour exists at all — the renderer probe (`canPlayNatively`) is a live check, so if that ever changes the native path unlocks itself with no code change.

- **WebVideoPlayerView** - `WKWebView`-based player (kept for WebM support). Native `controls` are off for the main video window; a custom-controls bridge is enabled by passing an optional `playbackModel: VideoWindowModel`. State flows JS→Swift over the `videoPlayback` message channel (`timeupdate`/`play`/`pause`/`seeked`/`volumechange`/`loadedmetadata` post `{currentTime,duration,paused,muted,buffered}`); commands flow Swift→JS via `play`/`pause`/`seek`/`setMuted` closures bound in `updateUIView`. The bridge is additive/optional — other callers (animated GIFs in `PhotoDisplayView`, remote-viewer videos, stereoscopic 2D fallback) pass no `playbackModel` and are unaffected. Error escalation has two independent forms: `fallbackVideoURL` swaps `src` **inside the page** (remote slideshow's raw → HLS tiers), while `onSourceUnplayable` reports up to Swift (main video window) so the re-route also re-resolves the renderer. **Autoplay is driven from inside the page** (`kickAutoplay`, retried on `loadeddata`/`canplay`, cancelled by an explicit pause): the bare `autoplay` attribute is dropped when the page loads into a WKWebView not yet in the window hierarchy, which is what left prev/next-switched videos sitting on a blank frame. `window._roomActive` is likewise baked into the HTML at load (and `lastIsRoomActive` seeded) so the room-activity JS never fires against a page that hasn't loaded.

- **NativeMetalVideoPlayerView** - Flat-video path used when the source is AVFoundation-decodable (`playbackRenderer == .nativeMetal`): `AVPlayer` + `AVPlayerItemVideoOutput` → per-frame `MTLTexture` → `MetalImageView`. **HDR and Dolby Vision play through the system's `AVPlayerLayer` instead** (`NativeVideoHostView` holds both over one AVPlayer): the first decoded frame's transfer function says PQ/HLG, and while adjustments and sharpening are neutral the frame output is detached and the system layer shows, with display criteria on the window as the film player does. AVFoundation hands HDR frames over still PQ/HLG-encoded, so the old BGRA-into-`bgra8Unorm` path showed every HDR video washed out and dim. With adjustments on, Metal draws HDR itself (half-float frames, an EDR layer tagged PQ/HLG; tvOS has no EDR flag). A Dolby Vision profile 5 frame (RPU attached, no primaries) never leaves the system layer. Preferred over WebKit for local/HLS sources; audio uses `.mixWithOthers` (see `AudioSessionConfig`) so it doesn't interrupt other apps. Falls back to `WebVideoPlayerView` on decode failure (`forceWebKitPlayback`). Being `.nativeMetal` — or being *reachable* via the server transcode, i.e. `pseudo3DAvailable` — is the gate for the fake-3D "Convert to 3D" option.

- **Cinema** (visionOS): the control strip's pinned Cinema button offers Big Screen and Head-Locked Sound here too; `CinemaVideoWindowHook` lends the native renderer's `AVPlayer` to the cinema space and keeps 3D and Big Screen exclusive. Design and open questions: `hypnos-film-player.md` → Cinema.

- **Skip and undo.** Every skip (the button, or a SponsorBlock auto-skip) can be undone for `LibrarySegmentSkipPolicy.undoSeconds` (10 s): `MediaSegmentSkipper.noteSkipped` / `takeUndo`, shown as `UndoSkipButton` ("Skipped Sponsor · Undo", a ring running down the time) in the prompt slot. Undo goes back to where the skip left from and that segment is no longer offered (the viewer chose to watch it; an auto-skip was already once-only). The film player and the Mac window show the same button; tvOS turns its contextual action into "Undo Skip …".
- **Menus and the playhead.** The player reports `currentTime` up to 30×/s. Nothing that renders an ornament menu may read it in its body: `VideoControlBar` freezes its state while any ornament menu is open, and `offeredSegment` is stored and written only on change. Either read re-rendered the open View Mode menu on every report (the "dropdown refreshes every second" bug). Picking a view mode closes the More popover (`closeOrnamentMenus`) so a stereo picture never engages under it.

- **Jellyfin WebM** keeps a full-quality HLS transcode in reserve (`GenericPlaybackPlan.transcodeURL` → `GalleryVideo.transcodeStreamURL`), like Stash, so AI 3D swaps onto it; a quality change replaces the reserve with the new plan's. Pre-processing downloads its `stream.mp4` sibling under its own play session.

- **StereoscopicVideoPlayer** - Coordinates download → MV-HEVC conversion → immersive playback. The immersive space is global (one at a time): `StereoscopicVideoView` registers `AppModel.immersiveVideoOwner` (the owning `VideoWindowModel`) on enter, and `ImmersiveVideoView` reads that window's `stereoscopicOverride`.

- **MVHEVCConverter** - Converts side-by-side/over-under stereoscopic video to MV-HEVC format. Lives in Vergence (`VergenceApple`) with `StereoscopicFormat` and its tag detection (`VergenceCore`); Hypnos keeps the config factories from a `GalleryVideo` (`MVHEVCConversionConfig+Library.swift`) and the Jellyfin `Video3DFormat` mapping (`StereoscopicFormat.swift`)

- **ImmersiveVideoView** - RealityKit-based immersive player in full immersion space

- **Video3DSettingsSheet** - Manual override for stereoscopic format detection

## visionOS player chrome

The video window and the film player hang the two-row control strip (RAVEUI's `.strip` `RAVEPlayerControls`, timeline over transport and buttons) under the window as an ornament at `.scene(.bottom)`, so the window is the picture alone; the system moves the window bar below the ornament. The strip and the window bar auto-hide together while playing (`isUIHidden`/`isWindowControlsHidden` in the video window, `chromeVisible` in the film player; tap the picture to bring them back) and stay up while paused, scrubbing or with a menu open. **They animate** (`PlayerChromeAnimation.swift`): `playerChromeOrnament` mounts the ornament hidden and springs the strip (and the title corner) into place, and on hide plays the fade-and-sink before taking the ornament down, since an ornament whose visibility turns hidden vanishes at once. The prompt (skip, undo, notices) slides between under the strip and the strip's place with it. iOS's ornament shim slides its edge overlays the same way. Feature buttons the strip has no room for move into its More popover by priority (see VideoOrnamentsView), which is why the video ornament's buttons use `OrnamentGlyph` (a title in the menu). There they render as grouped rows (Playback, Picture / Sound and Picture, Window) with flip, convergence and subtitle timing nudged in place (`PlayerStepRow`) rather than only in the Adjustments window. Under a stereo picture the bar sits `VideoWindowView.stereoControlsGap` (44 pt) below the window instead of 12, as the picture reads nearer than its edge. iOS keeps the stacked bar in its edge overlay.

**Stereo plane corners and edges.** `VideoPlayerComponent`'s screen mesh has rounded corners and no API to change them; with Settings → Rounded Corners off, the engine overscans the plane slightly (`Pseudo3DStereoEngine.squareCornerOverscan`) so the window's edge cuts them square. That only works where the window's edge *is* the picture's edge, which is why nothing may sit inside the window below a stereo picture. The plane is placed with `setPosition(_, relativeTo: nil)`: a scene-space centre set as the local position doubled any offset of the view inside its window (clipped top, gap and rounded corners below).

**Menus that never report closing.** Ornament menus count themselves open from their content's appear/disappear; one the system closes while the window is away (headset asleep, another app's immersive space) never decrements, which held the chrome and kept a stereo picture dimmed. `VideoWindowModel.clearLostMenus` and `FilmPlayerView.clearLostHolds` reset on background and on a tap on the picture (which closes any open menu first). While a menu is open the stereo picture takes no input, so the menu keeps the gaze (the engine re-enables it after 15 s in case a menu never reports closing); the bar's More is a popover rather than a Menu (a Menu holding submenus reported opening once and never closing), and while it alone is open the picture stays tappable and a tap only closes it (`pictureTakesInputWithChrome`, `menuDismissals`). The compact bar's speaker button opens a popover with mute and the volume slider (reported like More, so the chrome holds), which sets one shared, persisted volume (`PlayerVolume`) for every video window and the film player. Choices whose value matters mid-film show it on the bar as a badge (`PlayerBadge`, `PlayerChoiceMenu(badge:)`) instead of an icon: the view mode (2D / 3D / AI 3D / Immersive, filled while 3D is on, in the video window and the film player), stream and YouTube quality ("1080p"), and the film's picture tier and audio quality ("4K", "64k").
