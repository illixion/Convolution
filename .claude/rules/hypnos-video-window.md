# Hypnos: video window, flat players and stereo playback

## Network interruption checks

`apps.call videoNetworkTest` targets the active on-device Matroska player's remote file reads, without changing device networking or interrupting the debug server. Profiles: `outage` throws connection-lost errors; `slow` delays each read (`delaySeconds`, default 2); `off` stops the fault. `seconds` defaults to 30 and is capped at 600. `videoNetworkSamples` records clocks, buffer end, waiting/playing and fault counts once per second. This is transport fault injection, not a Wi-Fi packet-loss emulator, and does not affect server HLS or other apps. With multiple windows, it uses the first live native player; `available: 0` means that player is not using a device remux.

Let the existing buffer drain before calling a run a stall/recovery test (AVPlayer can keep several minutes). Do not seek or replace the player to force a stall in that test. Confirm fault counts increased and the player actually waited. Use `off` afterward. A long outage can exhaust AVPlayer's retries; Retry must retain the original remux and playhead. A transport failure must never be classified as an unsupported MKV and sent through WebKit/server transcoding. Genuine format fallbacks also carry the playhead, with no wall-clock expiry while waiting for a slow replacement to open.

Device evidence (2026-10-28): repeated connection-lost failures at segment 98, buffer ending at 613.525 s, unsolicited backward jump of about 5.6 s, then stall at 613.435 s. Before the fix the native failure switched to WebKit then server transcoding and lost position. After the fix the connection error retained 613.433 s; Retry used the original device remux, a decoded-picture comparison matched the expected source frame, and the user confirmed subtitles in sync with offset zero. This establishes the failure/fallback defect; it does not prove every earlier tracking-loss subtitle report had that cause. Trace: `build/debugtrace/traces/Convolution-trace-20261028-205401-054d521d.zip` (local validation artifact). Do not compensate these failures with per-episode subtitle offsets.

Moved out of `CLAUDE.md`. The fake-3D / depth pipeline is in `hypnos-ai-3d-video.md`; Jellyfin/Library streaming is in `hypnos-library-jellyfin.md`.

- **VideoWindowModel** - Per-window `@MainActor @Observable` model (mirrors `PhotoWindowModel`) owning the window's current video, navigation snapshot (own copy of `galleryVideos` + `currentIndex` + lazy pagination), 3D intent (`stereoscopicOverride`/`video3DSettings`), flip, per-window `currentAdjustments`, playback state (`currentTime`/`duration`/`isPaused`/`isMuted`/`bufferedEnd`/`isScrubbing`), the `VideoLoopController`, share state, and auto-hide timers. Side-effect-free `init`; side effects in `start()`; `cleanup()` on dismiss. This replaced the old shared `AppModel.selectedVideo`/`videoStereoscopicOverride`/`video3DSettings`/`isVideoFlipped`/`videoVisualAdjustments` + app-level auto-hide, so multiple video windows are fully independent (fixes the bug where every pushed window showed the last-selected video). Created with `@State` in `VideoWindowView(windowValue:appModel:)`.

- **A disconnected scene stops its player** (`SceneDelegate.onDisconnect` → `VideoWindowModel.sceneDidDisconnect`): SwiftUI gave a scene the system disconnected (a Summon's recycle, a window dropped at restore) no `onDisappear` and no dismantle, so its AVPlayer played on with no window, and at restore one even started after the disconnect (device, 2026-10-25). The player is paused and its item removed; one that appears later is silenced in `noteNativePlayer`. Picture windows (`PhotoWindowView`, `SharedPhotoWindowView`) run `PhotoWindowModel.cleanup()` at a disconnect too, giving back their textures (it can run again at a later onDisappear: `releasedWindow` keeps the window count right), and a slideshow window stops its engine (`RemoteViewerWindowView.tearDown`). The handlers hold their models weakly: a pushed viewer shares the gallery's scene, whose handlers outlive it. What stays is SwiftUI's own view graph for the dropped scene, which the app can't release.

- **A backgrounded window pauses its native player** (`pauseNativePlayerForBackground`, 2026-11-04), unless it is lent to the Big Screen. The app runs in the background for music (`UIBackgroundModes` `audio`), and this player has no `AVPlayerLayer`, so the system would let it play on unseen. Not resumed on return. **The screen stays on while a window plays** on iOS and tvOS (`IdleTimerHold`, from `isPaused`; the film player holds through it too): the Metal path has no layer to prevent display sleep, and an iPad went dark mid-episode.

- **VideoWindowView** - Thin wrapper handling both pushed and standalone modes via `wasPushed` (same pattern as `PhotoWindowView`). Picks the render path per `windowModel`: the stereo `Pseudo3DVideoPlayerView` (`showsStereoPicture`: AI 3D, or live 3D of a stereo video), else the flat player (`playbackRenderer`: `.resolving` → `.nativeMetal` `NativeMetalVideoPlayerView` → `.webKit` `WebVideoPlayerView`). Hosts one `RAVEPlayerControls` ornament for both 2D and fake-3D, with app actions supplied by `VideoOrnamentsView`. Locks window aspect ratio using **this** window's scene via `@Environment(SceneDelegate.self)` (not an arbitrary foreground scene); after each lock request a one-shot follow-up (`aspectRelockTask`) reads back the *granted* scene size and re-locks to a video-true size fitting inside it — portrait videos hit the platform's max window height, and a clamped grant under `.uniform` otherwise locks a wrong ratio (permanent letterbox between video and chrome, no room to enlarge). **Fake-3D chrome depth:** the ornament is kept coplanar with the visionOS window controls (`pseudo3DChromeZOffset = 0`; an earlier 20cm push floated the chrome off that plane and occluded the window controls) and the video is pulled back to that same plane by `Pseudo3DVideoPlayerView.videoPlaneZRecess` (90pt ≈ 9cm; the front-aligned `.frame(depth: 0, alignment: .front)` slab sits at the front of the window's depth region, measured ~9cm proud of the chrome on-device — the recess is applied as `.offset(z:)` on the GeometryReader3D so the fit math is unaffected; both constants stay tunable). `pseudo3DChromeBottomLift`/`ornamentBottomPadding` reserve the shared controls' footprint and keep it clear of the video and system window controls.

- **VideoControlBar** - Thin adapter from `VideoWindowModel` command closures to RAVEUI's `RAVEPlayerControls` in its `.strip` layout (every platform the window runs on): native SwiftUI scrubber, previous/next video around ±10s and play/pause (`RAVEPlayerNavigation`, when the window browses a list), volume, buffering, A/B markers, the skippable segments marked under the track (`MediaSegmentSkipper.markedRanges`) and the picture readout (`VideoWindowModel.pictureDetails`). WebKit, Metal and stereo all drive the same UI through the active renderer's closures. A drag seeks once on release; scrub/scroll lifecycles suspend auto-hide. On visionOS the strip is as wide as the window (`VideoWindowView.stripWidth`, 760…1180 pt).
- **Picture readout** ("1920×1080 · 23.976 fps"): `pictureSize` / `pictureFrameRate` on the model, written only on a change, cleared per video. The size comes from every renderer's `onVideoSizeKnown` (and the WebKit page's state reports, so an adaptive stream's new size shows); the rate from the native player's track (`nominalFrameRate`, else `currentVideoFrameRate` at 1×, polled every 2 s for HLS variant changes), the WebKit page's `requestVideoFrameCallback` media times (median gap over ~90 frames after each load and seek), or the stereo pump's `sourceFramesPerSecond`. Rates are snapped to the standard ones (`VideoPictureFormat`).

More holds what the strip had no room for and what is only ever there (flip, convergence and subtitle timing rows, All Adjustments, Slideshow, Pop Out, Open in Safari). The title is the window's own (below). The ViewMode menu switches **2D**, live **3D** (+ "Edit 3D Settings" when active), and **"AI 3D"** (formerly "Convert to 3D (Beta)"; named apart from "3D" so it reads as depth estimated from a 2D picture, not a 3D movie) — the fake-3D path (gated `disabled` to `windowModel.pseudo3DAvailable` — AVFoundation-decodable now, or reachable via the Stash transcode; realtime or pre-processed, see the engage flow below). The three modes are a **radio group** (`modeButton` + `currentViewMode`): exactly one carries the checkmark, selecting another switches directly, re-selecting the active one is a no-op (leaving a mode = picking another). There is no "3D Depth" preset submenu (strength is pinned — see `Pseudo3DSettings`; convergence lives in the Adjustments window); whenever fake-3D is available (`pseudo3DAvailable`) the menu also shows **both** depth-model submenus — **Depth Model (Real-Time)** and **Depth Model (Pre-Process)** — and this video's conversion progress + Cancel while a background conversion runs; the mode label reads `3D*` in fake-3D. Playback transport and feature actions share one `RAVEPlayerControls` ornament in both 2D and fake-3D. The More menu's **Adjustments** button opens the standalone `video-adjustments` window (`VideoAdjustmentsWindowView`) rather than a popover — it sets `appModel.videoAdjustmentsTarget`, so the panel is freely repositionable and never occluded by the front-plane fake-3D video; also Slideshow and Pop Out (when pushed). Info button opens `MediaDetailSheet`. Takes `@Bindable var windowModel`.

- **Playback info panel** (`Views/Videos/PlaybackInfoPanel.swift`, `Model/PlaybackInfo.swift`, `VideoWindowModel+PlaybackInfo.swift`; 2026-11-04): a semi-opaque card over the window's top-right corner, with the chrome (a visionOS ornament at `.scene(.topTrailing)`, an overlay on iOS and the Mac). Line 1 is the route (Direct Play, Remuxed on Device, Server Remux, Server Transcode, Web Player, YouTube Stream), tinted green for the original as it is, neutral for a chosen fallback (quality cap, AI 3D's 1080p, the MKV setting), orange when something failed; line 2 the picture readout (moved here from the control strip, which keeps it only when the panel is hidden) with the dynamic range; line 3 why. A tap opens the details popover ("Playback Info", a `popoverMenuNames` entry). **The range comes from the frames**: the native player's first frame per load and the stereo pump's `FrameColorSignal` (Vergence → `Pseudo3DStereoEngine.onFrameSignal`; the stereo players never apply an RPU, so Dolby Vision reads as its base layer there), named with the source's metadata (Jellyfin `VideoRangeType`/`DvProfile`, or the remux summary's `dolbyVisionProfile`) by RAVEMediaCore's `VideoDynamicRange` ("SDR, tone-mapped from Dolby Vision 8.1"). **The reasons are noted where each fallback happens** (`notePlaybackRefusal`: a remux decline with `MatroskaRemuxService.declineReason`, the native player failing, WebKit failing) plus why a Library stream is at its level (`streamLevelReason`). For a Jellyfin stream `watchServerTranscode` polls `/Sessions?deviceId=` for TranscodingInfo (video/audio copied or converted, reasons), which also decides Server Remux vs Transcode. A failure that hands the video to the server also posts a notice under the window. Settings → Videos → Playback Info: Always / When Something's Off / Never. Debug query `videoPlayback` returns what the panel shows. Seen on the AVP 2026-11-04 (a remuxed HDR10 episode); the server and failure paths are not yet seen on a device.
- **Title and details** - `PlayerTitleButton` (`Views/Videos/PlayerDetails.swift`) names what plays in the top-left corner, with the chrome: on visionOS an ornament at `.scene(.topLeading)` over the window's corner (SwiftUI can't draw over a stereo picture), on iOS beside the close button. An episode reads as its series over "S1 E3 · Title". A tap opens the details in a popover ("Details", one of `popoverMenuNames`, so a tap on the picture closes it): a Library title's series, episode, year, runtime, ratings, genres and overview from `LibraryService`, a Stash scene's studio, date, performers, tags and description from `fetchSceneDetail`, otherwise the file and its picture (`PlayerDetails(video:)`, shown until the server answers). The film player has the same corner (visionOS, iOS, and a focusable corner button with a details sheet on tvOS); tvOS's video player hands the same details to AVKit's own Info panel instead (see the tvOS rule).
- **Next episode carries on** (`VideoWindowModel.EpisodeCarryOver`): an episode that autoplays the next one hands it AI 3D (real-time, or the next episode's conversion when it has one; not while the window holds the Big Screen), the stream level Auto had settled on (the 1080p AI 3D starts at, or a step down for a stalling connection; fetched with `streamPlan(quality:forAI3D:)` before the switch, so the next episode doesn't start high and step again), and "already told 3D can't keep up". A video picked by hand starts afresh, as before.
- **Playback speed** - `PlaybackSpeedMenu` (`PlayerQuickControls.swift`, 0.5–2×, its badge filled when not 1×) sits with the Playback choices on the bar and in More, in the video window and the film player. `VideoWindowModel.playbackSpeed` is per window: kept through every renderer change and the next video, never restored with the window. Renderers take it like the volume: read at load (`defaultRate` on each `AVPlayer`, so every `play()`, loop and involuntary resume keeps it; `defaultPlaybackRate` in the WebKit page, which a source swap resets to) and live through `setSpeedCommand`; the immersive player reads its owner's. The Cinema screen shows the window's own player, so it follows. **Speed changes the frame rate** (since 2026-11-01): a 60 fps video at 2× shows all 120 frames a second, 0.5× shows 30, in 2D, 3D and AI 3D alike. Vergence's `PlaybackFrameRate` is the arithmetic (snap, × Smooth Motion's doubling, × speed, up to 120). The native Metal player's `MTKView` draws at `drawRate` (60, or 96 with Smooth Motion, times a faster speed) and states display criteria at the rate shown whenever the speed isn't 1×; the stereo engine's pump ticks at `drawRate` (`StereoPump.setFrameInterval` on a speed change) and states the same criteria; the film player's `FilmVideoPlayer.displayCriteria` multiplies by `rate`. tvOS keeps the film's rate in its criteria (a TV would switch mode, blanking, at every speed change). Real-time AI 3D is no longer held to the 1× frame count (`RealtimeDepthSource.limitsToSourceFrameRate` is false): its held-map interval is wall time, so more frames share each map, and the keeping-up report counts every frame the playhead passed (up to the ticks), so a model that can't keep up at 2× trips the 3D overload step-down. An M2 Vision Pro tops out at 100 Hz, so 120 fps content there shows what the display can. tvOS and the Mac video window are AVKit's players, whose own speed menu is left on.

- **VideoLoopController** - `@Observable @MainActor` per-window model (owned by `VideoWindowModel`) for the A-B loop on the 2D web player. Cycles `idle → aSet → active → idle`: 1st press sets A, **2nd press sets B and engages immediately** (no confirmation step), 3rd press (or the control-bar clear button → `clear()`) disables. Owns its own toast state. Wires `queryCurrentTime`/`setLoopBounds` closures bound by `WebVideoPlayerView` to the JS rVFC monitor (`window.__startABLoop` / `window.__stopABLoop`).

- **Stream-URL strategy (Stash scenes)** - `GalleryVideo.streamURL` is **always the server's original file**; `transcodeStreamURL` holds Stash's live transcode (HLS `/stream.m3u8` preferred, else the non-seekable fragmented `/stream.mp4`) as a *reserve*, populated for every scene advertising endpoints when Settings → Server-Side Transcoding is on (`enableStashTranscoding`, default on). WebKit decodes WebM (VP8/VP9) on-device, so nothing transcodes up front. The transcode is engaged in exactly three cases: (1) the WebKit player reports the original unplayable — a decode/unsupported-source error immediately, a network error after its retries — via `onSourceUnplayable` → `VideoWindowModel.handleSourceUnplayable()`; (2) any fake-3D or live 3D engage, and Big Screen, on a WebKit-decoded source (`enablePseudo3D()`, `enable3DMode()`, `CinemaVideoWindowHook`); with no transcode, live 3D plays flat with a notice (`live3DUnavailable`); (3) `transcodedDownloadURL` (depth pre-process), which prefers the transcode rewritten to `/stream.mp4` because AVAssetReader can't read WebM at all. `VideoWindowModel.activeStreamURL`/`usingTranscodedStream` track which one is playing (reset per video switch); `canUseTranscodedStream` and `pseudo3DAvailable` gate the UI. **AVFoundation still cannot open the WebM or Matroska container on visionOS 27** (VP9+Opus WebM fails `isPlayable` with -11828, -11850 over HTTP, though the same streams in MP4 play), so an original the renderer probe (`canPlayNatively`) refuses is first offered to the on-device remux below; WebKit and the transcode are what's left when that declines.

- **Matroska remux** (`Services/MatroskaRemux/`, the `Packages/MatroskaRemux` package): an MKV/WebM original the native player can't open is remuxed to fragmented-MP4 HLS on the device, segment by segment as the player asks, and served from `LoopbackHTTPServer` (127.0.0.1). Lossless (no re-encode, no ffmpeg, no temp files), it starts in milliseconds (a 1.1 GB UHD remux opens in ~0.15 s) and keeps what WebKit loses: HDR, Dolby Vision, spatial audio, the native player's features, real-time AI 3D. `resolvePlaybackRenderer` tries it after a failed probe and before WebKit and the transcode; the result is `VideoWindowModel.remuxedStreamURL`, which `activeStreamURL` returns in place of the original the way `resolvedPhotosStreamURL` does. **`video.streamURL` is never overwritten**: a restored window's loopback URL is dead after a relaunch, and the original is what it resolves again. `canTryRemux` keeps it off Photos assets, YouTube, Library titles playing a stream Jellyfin made (`JellyfinLibrary.isFileStream` lets through the file itself: a WebM, or an MKV with Settings → Jellyfin → **Play MKV Files on This Device**, `library.remuxOnDevice`, on by default, for which `streamPlan` returns the file with the server's remux in reserve) and anything playing a transcode or AI 3D tier. A Library title remuxed this way takes its embedded subtitles from the file and only the sidecars from the server (`SubtitleSource.excludingEmbedded`), and its audio tracks from the remux's renditions; checked on the Mac 2026-10-25 against the dev Jellyfin (`Two Voices`, `Subtitle Window`). If the native player then fails on the remux, `forceWebKitPlayback` drops it (`remuxRefused`) and WebKit gets the original, as before. AI 3D plays the remux's HLS like YouTube's; the depth pre-process and MV-HEVC conversion still read the transcode (`transcodedDownloadURL`), since AVAssetReader reads neither WebM nor HLS. tvOS (`TVVideoPlayerView.resolve`) tries it between the failed probe and the transcode; the Mac has the video window itself.
  - **What it carries.** Video H.264, HEVC (`hvc1`; an hvcC without parameter sets, as Netflix WEB-DLs ship with the VPS/SPS/PPS only in band, gets them from the first keyframe, since VideoToolbox has no decoder for `hev1` with an empty hvcC (-12906) and such a title used to fall to a single-audio server transcode; `hev1` only when the keyframe lacks them too), VP9 (`vpcC` from CodecPrivate, else the first keyframe's header, plus the track's Colour), AV1 where the chip decodes it. Audio AAC (legacy `A_AAC/MPEG4/*` ids too), AC-3, E-AC-3, Opus, FLAC, ALAC, MP3 (as QuickTime's `.mp3` entry with CODECS `mp4a.40.34`: AVFoundation refuses MP3 as ISO `mp4a`/0x6B, even in a plain MP4). Each audio track is its own `EXT-X-MEDIA` rendition with its name, language and default flag, so the player's audio menu works. **What the menu shows:** AVKit lists each option's `displayName`, which AVFoundation makes from LANGUAGE alone (NAME only becomes the option's common title metadata, `m3u8/NAME`): no LANGUAGE reads "Unknown", `und` "Unknown language", `mul`/`zxx` "Multiple languages"/"No linguistic content", private-use tags read as code, and a value it can't read as a language is shown verbatim (measured against a loopback master, `RenditionLabelTests`). So a track with a stated language keeps its tag (shown as the language, and auto-selected by preferred language); one without carries its NAME as LANGUAGE (its track name, else codec and layout: "AC-3 5.1", "AAC Mono"); where tracks share a language the default keeps the tag and the others show their NAME; a NAME that reads as a language code ("de") gets its layout added. `RemuxSession.audioRenditions` hands the app each rendition's NAME, stated language, codec, channels, layout, object-audio flag and default flag for a menu of its own (match an `AVMediaSelectionOption` by its title metadata, the NAME). Declined (the caller keeps its fallback): VP8, a file whose audio is all unsupported (Vorbis, PCM; DTS and TrueHD outside the sideload edition, below), encrypted or zlib-compressed tracks, a server's file without Cues whose clusters have no sizes (a live MediaRecorder WebM; a local one is scanned); unsupported audio next to a supported track is just dropped (TrueHD beside E-AC-3). Before answering, `MatroskaRemuxService.canDecode` asks VideoToolbox for a decoder of the remux's own sample entry (no AV1 before M3/A17 Pro), then the decode probe opens the result.
  - **DTS and TrueHD, sideload edition only** (`HYPNOS_FFMPEG`, 2026-11-01; App Store builds never decode them, CLAUDE.md). The remux takes a decoder from its caller (`RemuxOptions.audioDecoding`, `AudioTranscode.swift` in the package); the app passes FFmpeg's (`Services/MatroskaRemux/FFmpegRemuxDecoding.swift`), so such a track becomes a rendition like any other, as **lossless 24-bit ALAC**, labelled with its source codec ("DTS 5.1"). AVPlayer plays 5.1 ALAC in fMP4 HLS (measured on the Mac; 5.1 FLAC from ffmpeg was refused, -12927). Each segment is decoded with a fresh decoder from its own frames plus the previous segment's last 0.25 s, then laid over the frames' span from the end, so a re-requested segment is the same bytes: without the priming a fresh DTS filterbank left the first ~80 ms of every segment wrong (38 dB SNR), with it the rendition matches FFmpeg decoding the whole track (112 dB on Ready Player One's DTS core; exact for the fixtures). The ALAC is escape (uncompressed) frames written by the remux itself, exact for any packet length: 6.9 Mbps for 24-bit 5.1, loopback only. TrueHD access units are 1/1200 s, under Matroska's millisecond tick, so block times collide; each unit is placed by its own 16-bit `input_timing` sample counter instead (the block time only resolves the counter's wrap). Channels go into ALAC's default order (C L R Ls Rs LFE; side or back surrounds as Ls/Rs); **7.1 isn't mapped yet** and such a track is still dropped (ALAC's 8-channel default is C Lc Rc L R Ls Rs LFE, so it needs a `chan` box, untested). DTS:X and Atmos objects are not decoded: DTS gives its core or lossless channels, TrueHD its channel presentation. The decoders: `Packages/FFmpegDecoders`, a Swift wrapper that dlopens `HypnosFFmpeg.framework` (FFmpeg 9.0.2's dca/truehd/mlp decoders and parsers plus `Shim/shim.c`, LGPL, built by `scripts/build-ffmpeg-decoders.sh` into the gitignored `HypnosFFmpeg.xcframework`). **Nothing links it**: the app target's "Embed FFmpeg decoders (sideload only)" phase copies the framework into Frameworks/ only when `HYPNOS_FFMPEG` is set and removes it otherwise. A static library was tried first and was in every build, flag or not, Release included (SwiftPM links package objects whole). Checks: `swift test` in MatroskaRemux (`TranscodeTests`, DTS and TrueHD 5.1 fixtures with a tone per channel spanning two segments: declined without a decoder, ALAC channel order, same bytes per segment, sample-exact against a straight-through decode) and `swift run mkvremux <file> <folder>`, which loads the framework when built. **On the headset (2026-11-01):** Ready Player One's DTS played remuxed (ready in 1.3 s, head-tracked multichannel) in live 3D with Smooth Motion at ~47 fps, nothing late. Not yet tried: a real TrueHD film, and the CPU cost of decoding measured with `_profile`.
  - **Stable Audio** (the switch under the volume slider, `StableAudio.swift` in the package, `Services/MatroskaRemux/StableAudioSetting.swift`; 2026-11-01, moved out of Settings 2026-11-02). Every remuxed audio track that something on the device can decode also gets a levelled copy, a second rendition "<track's name> (Stable)" (`RemuxOptions.stableAudio`; rendition number = track number | `AudioPlan.stableFlag`, 1<<40). DTS and TrueHD are decoded anyway (FFmpeg, sideload only). AAC, AC-3 and E-AC-3, which play as they are, get a copy decoded by **AudioToolbox** (`SystemAudioDecoding.swift`, every build, App Store included: the OS codec does the decoding). Processing, on 10 ms blocks: speech is the centre (stereo: mid) channel with >40% of its power in 250 Hz-3.5 kHz above -55 dBFS; while it lasts the other channels duck to at most 4 dB over the dialogue (≤ 9 dB, 400 ms back); +3 dB at 2.8 kHz on the centre; the dialogue is levelled to -27 dBFS (±9 dB), loudness over -20 compressed 3:1, nothing below -60 lifted; a 5 ms look-ahead limiter at -1 dBFS. Each segment is primed with 2 s of the previous one (`StableAudio.primingSeconds`), so seams are >30 dB below the signal and segments stay byte-identical. On 6 minutes of Ready Player One: loudness range 21.2 → 12.7 LU, short-term p10/p99 -39.4/-9.3 → -31.0/-16.8 LUFS, centre +2.6 dB against surrounds/LFE -5 to -7 dB; ~2 s of processing per 6 minutes on the Mac.
    - **The copies are never in the Audio menu.** `VideoWindowModel.stablePairs` pairs each copy with its track by name: the copy's NAME is exactly the track's final NAME plus `AudioRendition.stableSuffix`, which is why copies are left out of duplicate-name disambiguation in `Playlists.swift`. The switch (`setStableAudio`, remembered for every video in `video.stableAudioOn`) selects the counterpart in whichever player plays, the native renderer's or the stereo engine's (`noteStereoAudioPlayer`, which also gives 3D the Audio menu), and `refreshAudioTracks` enforces it whenever the options load. While it is on, a remux lists the copies first with DEFAULT=YES and the language tag, so a player starts on them (`StableRenditionTests.aPlayerStartsWithTheRightCopy`). A cached session opened with the switch the other way is reopened once no player has read it for 30 s.
    - **A copy of a passthrough track is parsed on that track's timeline** (the segment parser keys plans by track number): `AudioPlan.retimed` moves each frame onto the copy's rate (HE-AAC decodes at twice its core rate) and earlier by `leadingSamples`, 2112 for AAC, because AVFoundation trims Apple's standard AAC priming from the track itself (an ffmpeg-encoded file really has 1024, so the track plays ~23 ms early and the copy must match it, not the truth). Frame lengths come from the codec, not from decoding the first frame: AudioToolbox's AC-3 decoders put out 1248 of the first 1536 samples and hold the last 288 back, so `SystemAudioDecoder.finish` feeds the last packet again and cuts to the packets fed. `systemDecodedCopyKeepsTime` checks a click a second lands on the same sample in the track and its copy; AC-3 puts out L C R Ls Rs LFE, AAC C L R Ls Rs LFE.
    - **The volume popover's state stays live while a menu is open.** `VideoControlBar` freezes the bar's state while any ornament menu is open, and the volume popover counts as one, so the slider and mute read the volume from when it opened: the slider fought the finger, and dragging while muted toggled mute on every step. Volume and mute now come from the model even while frozen, RAVEUI's slider keeps its own value during a drag, and it unmutes once per drag.
  - **HDR.** Colour goes into the sample entry as `colr`/`mdcv`/`clli` (CoreMedia reads all three, `vp09` included: checked against ffmpeg's MP4 of the same stream) and VIDEO-RANGE comes from the Colour element, else the HEVC/H.264 SPS or AV1 sequence header. Dolby Vision profile 8 keeps `hvc1` plus its dvvC/dvcC box and SUPPLEMENTAL-CODECS; profile 5 is `dvh1`; the RPU is never touched. **A player that can't present HDR refuses an HDR master outright** (`AVPlayer.eligibleForHDRPlayback` false: CoreMedia -17223, or -12927 with the range left out; ffmpeg's own HLS too), while it plays the same picture from a media playlist, tone-mapped. Such a device (an SDR TV, a Mac on an SDR display) gets the session's `muxed.m3u8`: video and the default audio in one stream, without the audio menu.
  - **Audio must cover the video.** AVPlayer's HLS clock runs on audio: where an audio rendition runs out before the video, playback stalls there for good (and with audio that starts late, it starts only where the audio does); plain MP4 plays through, so does nothing here. Each audio segment therefore covers its whole span: a gap is bridged by lengthening the sample before it, a stretch with no frames (a track that starts late, a hole in one) gets one placeholder sample as long as the stretch. **The placeholder is a frame of silence** built for the track's own configuration (`Codecs/SilentFrames.swift`); it used to be the track's first frame, a blip of the soundtrack. AAC (Main/LC/SSR/LTP and HE-AAC's LC core, channel configurations 1–7): a raw_data_block whose ICSs have max_sfb 0. AC-3 and E-AC-3: a syncframe with the stream's rate, channel mode, LFE and frame size, flat exponents, coarse and fine SNR offsets 0 (A/52: no bits allocated) and dither off, CRCs computed (crc1 solved over GF(2)); E-AC-3 only for one independent substream without object audio. Opus: libopus's own silence, `F8/FC FF FE` per stream (self-delimited in a multistream packet). FLAC: the stream's first frame header over CONSTANT 0 subframes (Apple's decoder refuses a frame that leaves block size, rate or sample size to STREAMINFO). ALAC (mono, stereo): an escape frame of zeros. MP3: a frame without main data. The rest keeps the first frame: an AAC channel configuration of 0 (needs the PCE), ER AAC, E-AC-3 7.1 or with object audio, ALAC beyond stereo, free-format MP3. Checked by decoding with AVFoundation (exact zeros for every fixture codec, AAC configurations 1–7 and HE-AAC, AC-3 in all 16 channel modes, E-AC-3 mono/stereo/5.1, and a late track's lead-in) and by splicing them between real frames for ffmpeg with CRC checks on (silence, then the real frames at their level).
  - **A server's file is read once, in pieces, never whole.** Opening reads the head and the Cues (a few hundred KB); each segment is one range request when the player asks for it, so the player's own forward buffer (about 60 s on the Mac) is all that is fetched ahead, and a seek fetches the target segment, nothing in between. Measured over HTTP (2026-10-25, a logging range server): a 5-minute 8 Mbps MKV played 20 s + seek + 20 s read 150 MB of 306 with nothing twice; the 1.1 GB UHD Dolby Vision demo read each byte once (0.2 % repeated). Two things made that: a request's parse is shared by its video and audio (`muxedSegment` used to look it up twice, and a 100 MB UHD segment is over the 64 MB parse budget on its own, so the second lookup read it again), with each parse's audio kept for 16 segments (`parsedAudio`) for an audio rendition trailing its video; and the bytes a segment reads past its end (audio stored after the next keyframe) are kept for the next segment's read (`RecentReadsSource`), which used to fetch them again (4 % of a 1080p file, 13 % of a UHD one). AVFoundation's own refusal of an MKV over HTTP reads 0.5–1.6 MB.
  - **A server's file without Cues is indexed while it plays** (`ClusterHopper`, `ProgressiveIndex.swift`; a local one is still scanned before `open` returns). Every cluster states its size, so the index hops from one to the next reading only its head: the Timestamp and the block headers up to the first video block, which says whether the cluster starts on a keyframe; those clusters are the segment boundaries (the same ones Cues give, checked against every fixture). ffmpeg puts an audio block or two ahead of the keyframe in its cluster (and writes a CRC-32 first), mkvmerge nothing, so the first read follows what the last clusters needed (64 B to 4 KB) and a longer block ahead of the video is hopped over by its size. ffmpeg's clusters also break every 5 s mid-GOP; those just aren't boundaries. A 2-hour file is 1,500 to 3,600 clusters, a round trip each, so up to four chains hop at once (only for many small clusters): a probe read of twice a cluster's length at each quarter finds a Cluster ID with a Timestamp (or CRC-32) after it, and a chain stops where it lands exactly on the next one's start; a stray ID inside a frame starts a chain nobody joins. `open` waits for three segments, and for the whole index if, at its rate, it will be done within 1.5 s (`indexWait`): then the playlists are plain VOD. Otherwise they are **EVENT playlists** that list the committed segments, keep the target duration they had at `open`, carry `EXT-X-START:TIME-OFFSET=0` (without it AVPlayer starts three target durations from the end: 210 s into a 240 s playlist) and get `EXT-X-ENDLIST` when the index is done; the player's duration is indefinite until then (the app's players read that as 0), a seek past the listed part waits and plays once a reload lists it, and an over-long segment plays (all measured on the Mac). `SegmentIndex.Builder` commits a boundary only once no later keyframe could move it, so a listed segment never changes. Measured on a 922 MB 2-hour H.264 + AC-3 5.1 file with 2 s GOPs (3,600 clusters), logging range server: Cues 18 ms to open; no Cues, ffmpeg's layout, 0.63 s to a complete index on loopback (VOD), 2.8 s with 2 ms a request and 12.7 s with 10 ms (open in 70–250 ms, EVENT), 3,612 requests and 7.8 MB for the index; mkvmerge's layout 0.75 / 2.8 / 12.4 s and 2.2 MB. The heads the index read are read again with their clusters: playing 4 s, seeking to 70 % and to the end sent 75.7 MB with 0.43 MB twice (ffmpeg's 1.6 KB heads) and 70 MB with 20 KB twice (mkvmerge's). Without Info's Duration the end comes from the last video cluster's frames.
  - **The output starts at 0.** The player's clock starts at the first segment whatever its timestamps say, so the remux shifts the file's earliest frame to zero (not only a negative one, as before): a file cut from a recording starts at 7 s or an hour, and the subtitles below are timed on this timeline.
  - **Subtitles** don't go into the HLS (every player draws its own, in both eyes when stereo). The session lists the file's tracks (`subtitleTracks`: SubRip, ASS/SSA, WebVTT, PGS; VobSub and others listed, not selectable) and reads their blocks near the playhead (`subtitleBlocks(track:from:through:)`): mkvmerge and ffmpeg put every subtitle block in the Cues with its place in the cluster, so a line is two small range reads (the cluster's header, then 4 KB), never the video around it; a track without that index gets the blocks of the segments the player fetches, as every parse keeps the subtitle blocks it passes. zlib-compressed subtitle tracks are inflated. The app side is `SubtitleSource.matroska` (`Services/Subtitles/MatroskaSubtitles.swift`): a `live` track reading 15 s before to 120 s after the playhead once a second (the 40 lines around a seek arrive in ~0.3 s over a 15 ms link), text put into SubRip for the shared parser (ASS keeps italics, bold and `\an` top placement), PGS given back its .sup headers for `PGSSupFile`. `SubtitleSource.forVideo(_:remuxing:)` adds them after the sidecars once the remux is what plays (the video window reloads its subtitles then; tvOS builds its source after resolving). The Mac has them through the video window (checked 2026-10-25: a Stash MKV's SRT drawn with its italics).
  - **Grid thumbnails of MKV and WebM** come from the same package: AVAssetImageGenerator can't open Matroska, so `VideoStill.make` writes the smallest MP4 that has one frame (the video's init segment and one fragment with a single keyframe at time 0) and AVAssetImageGenerator opens that from a temporary file (`Services/MatroskaRemux/MatroskaThumbnails.swift`, two at a time). The keyframe is the one at or before a tenth of the way in (the first frames are often black), at most ten minutes in: a cue point, or without Cues a 256 KB probe at that share of the bytes for a Cluster, then hops to one starting with a keyframe. It is the fallback where the normal path fails: `ThumbnailGenerator` for a local file (after AVAssetImageGenerator, or for WebM after WebKit's capture on iOS and visionOS; tvOS and the Mac had nothing for WebM), and `ImageLoader.loadMatroskaThumbnail` for a server's video whose preview didn't load (Nextcloud renders none for Matroska without its movie preview provider), cached under the thumbnail URL. Stash makes its own and is never asked. Measured on the 2-hour file at 10 ms a request: 4–7 requests, 0.4–0.6 MB (the head, Cues or the probe, the keyframe's cluster start), 0.1–0.2 s before AVAssetImageGenerator; the harness logs each input's thumbnail through the app's own path. VP8 (not carried) still gets none outside WebKit.
  - **Checks.** `swift test` in the package (fixtures plus AVFoundation decoding every frame of each; the subtitle fixtures and server-read tests too; cue-less files are made in memory by voiding a fixture's Cues or with `MatroskaTestWriter`), and the DEBUG macOS harness, `Hypnos -RemuxHarness <files or URLs> [-RemuxHarnessForm master|muxed] [-RemuxHarnessHold <s>] [-RemuxHarnessPlay <s>]`, which plays each through the app's real path (probe, format descriptions, 3 s of frames or `-RemuxHarnessPlay`'s, for an EVENT playlist how long until its duration is known, audio switch, a seek to 70 %, playing to the end), reads each subtitle track's cues near the start and 70 % through `MatroskaSubtitles`, and can hold the server for `ffmpeg -i http://127.0.0.1:<port>/remux-…/master.m3u8 -f null -`. For what a server file costs, serve it from a range server that logs each request (the dev Stash, or a throttled one) and add up the ranges; `swift run -c release mkvremux --time <URL>` times opening and indexing one.

## visionOS player chrome

The video window and the film player hang the two-row control strip (RAVEUI's `.strip` `RAVEPlayerControls`, timeline over transport and buttons) under the window as an ornament at `.scene(.bottom)`, so the window is the picture alone; the system moves the window bar below the ornament. The strip and the window bar auto-hide together while playing (`isUIHidden`/`isWindowControlsHidden` in the video window, `chromeVisible` in the film player; tap the picture to bring them back) and stay up while paused, scrubbing or with a menu open. **They animate** (`PlayerChromeAnimation.swift`): `playerChromeOrnament` mounts the ornament hidden and springs the strip (and the title corner) into place, and on hide plays the fade-and-sink before taking the ornament down, since an ornament whose visibility turns hidden vanishes at once. The prompt (skip, undo, notices) slides between under the strip and the strip's place with it. iOS's ornament shim slides its edge overlays the same way. Feature buttons the strip has no room for move into its More popover by priority (see VideoOrnamentsView), which is why the video ornament's buttons use `OrnamentGlyph` (a title in the menu). There they render as grouped rows (Playback, Picture / Sound and Picture, Window) with flip, convergence and subtitle timing nudged in place (`PlayerStepRow`) rather than only in the Adjustments window. Under a stereo picture the bar sits `VideoWindowView.stereoControlsGap` (44 pt) below the window instead of 12, as the picture reads nearer than its edge. iOS keeps the stacked bar in its edge overlay.

**Stereo plane corners and edges.** `VideoPlayerComponent`'s screen mesh has rounded corners and no API to change them; with Settings → Rounded Corners off, the engine overscans the plane slightly (`Pseudo3DStereoEngine.squareCornerOverscan`) so the window's edge cuts them square. That only works where the window's edge *is* the picture's edge, which is why nothing may sit inside the window below a stereo picture. The plane is placed with `setPosition(_, relativeTo: nil)`: a scene-space centre set as the local position doubled any offset of the view inside its window (clipped top, gap and rounded corners below).

**Menus that never report closing.** Ornament menus count themselves open from their content's appear/disappear; one the system closes while the window is away (headset asleep, another app's immersive space) never decrements, which held the chrome and kept a stereo picture dimmed. `VideoWindowModel.clearLostMenus` and `FilmPlayerView.clearLostHolds` reset on background and on a tap on the picture (which closes any open menu first). While a menu is open the stereo picture takes no input, so the menu keeps the gaze (the engine re-enables it after 15 s in case a menu never reports closing); the bar's More is a popover rather than a Menu (a Menu holding submenus reported opening once and never closing), and while it alone is open the picture stays tappable and a tap only closes it (`pictureTakesInputWithChrome`, `menuDismissals`). The compact bar's speaker button opens a popover with mute and the volume slider (reported like More, so the chrome holds), which sets one shared, persisted volume (`PlayerVolume`) for every video window and the film player. Choices whose value matters mid-film show it on the bar as a badge (`PlayerBadge`, `PlayerChoiceMenu(badge:)`) instead of an icon: the view mode (2D / 3D / AI 3D, filled while 3D is on, in the video window and the film player), stream and YouTube quality ("1080p"), and the film's picture tier and audio quality ("4K", "64k").

## Translated subtitles (iOS and macOS only, 2026-10-27)

The subtitle menu's **Translate…** opens `SubtitleTranslateSheet`: the source (a YouTube video's automatic captions, or AI Captions), its language (fixed for YouTube's track, a speech-locale picker for AI Captions) and the destination (Settings → AI Captions → Translate To, `translation.target`, empty = the system language). **Apple's Translation framework is marked unavailable on visionOS and tvOS, even in the 27.0 SDKs**, so the item, the sheet and the setting exist on iOS and macOS only (the user chose that over a Foundation Models route on visionOS); `SubtitleTranslator` is a no-op shell elsewhere. Languages not on the device are downloaded in the sheet (`.translationTask` + `prepareTranslation`, Apple's consent UI); translating runs headless on `TranslationSession(installedSource:target:)`. The source cues are translated in batches of 40, nearest the playhead first, and the translated track is republished after each batch; translations are cached by source text, which is what lets AI Captions' revisions and repeats cost nothing. For AI Captions the sheet's speech locale is lent to `RAVEGeneratedCaptions.start` for that one call (it reads `captions.locale` before anything else) and then put back. Any other subtitle pick, `reset` or `selectGenerated` stops the translation. Not yet exercised against real downloaded language packs: built on all four platforms only.

## Smooth Motion (frame interpolation, 2026-11-01)

Doubles 24–30 fps pictures with VideoToolbox's low-latency interpolator (the only one visionOS has: `420v`, ≤1080p) to ease motion sickness on slow pans, and (flat 2D only, 2026-11-04) 50–60 fps pictures to 100–120 with Vergence's GPU interpolator. Settings → Videos holds the default (`AppModel.smoothMotion`, visionOS only); each window's View Mode menu overrides it for that video (`VideoWindowModel.smoothMotionOverride`, reset on `switchToVideo`; `smoothMotionApplies` decides when the row shows), and so does the film player's (`FilmPlayerView.smoothMotionOverride`).
- **AI 3D:** Vergence's `InterpolatingFrameSource` wraps the pump's frame source before depth and warp, so both eyes come from one interpolated picture. It shares the Neural Engine with the depth model, which once made every frame late and drifted the picture behind the sound (device, 2026-10-31).
- **`InterpolationGovernor` steps by what it measures, not by thermal state** (the user's call, 2026-11-01: a headset reported `.serious` the moment a 2D video opened and a thermal stop never resumed). Too slow (median of 12 interpolations over 80% of a real frame's spacing) or a low reserve → in-between frames made at ⅔ size (1080p → 720p, 5.4 vs 17.9 ms on an M2 Max; real frames stay full size) → paused; frames already late pause at once; 20 s of headroom steps back up; three pauses a minute → off for that picture. `.depthPump` / `.flat` thresholds.
- **Flat 2D:** `NativeMetalVideoPlayerView.rebuildFramePresenter` puts the same source behind an `InterpolatedFramePresenter` (shows each frame when due; the source reads a real frame ahead), with `.flat` thresholds, a 96 Hz MTKView (it never asks past `lead`: unbounded read-ahead once held 10 s of 1080p frames, hit critical memory pressure and failed the player item, `-11819`) and doubled display criteria. SDR only (HDR stays on the system layer or half-float frames), no reload when toggled.
- **Packed stereo (Blu-ray 3D, SBS/TAB, half or full) only with an analysis track**: a file in Documents/Smooth Motion named by Jellyfin item id or title, made on a Mac by `vergence analyze`, else the Jellyfin plugin's track for the item, which it analyses nightly on a Mac server and serves in 10 s chunks read around the playhead (`SmoothMotionTracks`, Vergence's `StreamingAnalysisTrack`; JellyfinPlugin/README.md, "Smooth Motion tracks"). The film player (`FilmSession.sharedFields`) and the video window's live 3D (`VideoWindowModel.sharedFields`) hand it to the engine, which makes both eyes from the left eye's one motion field (`SharedFieldInterpolator`; plan and results in `docs/plans/blu-ray-3d-smooth-motion.md`). The menu row shows only while a track exists. While it doubles, the 3D picture states 2× display criteria.
- **Stripes (`InterpolationGuard`, Vergence, 2026-11-02):** VideoToolbox's low-latency interpolator (visionOS has no other; the higher-quality frame-rate conversion is macOS/iOS only) matches evenly spaced stripes (House's out-of-focus blinds) to the wrong stripe, so the in-between frames show them shifted by about half their spacing in a patch with bent edges, and the patch flickers at 48 Hz in 2D and AI 3D alike. It happens on still stripes (S03E15 8:37) and worse when the camera pans across them (37:29: a fifth of the frame wrong). A Metal pass after it finds each 16×16 tile's motion between the real frames by block matching (symmetric shift up to ±12 × ±3 px, coarse then refined, a small preference for slow motion picking the right stripe), and where the in-between frame strays far from the real frames' blend at that shift, and they matched well, it takes that blend instead. Tiles already close to the plain blend skip the search. On the pan it fixes 14% of the pixels; on a moving corridor shot it touches about 1%. GPU about 0.6–0.9 ms at 1080p on an M2 Max (so perhaps 2–3 ms on the headset), added to the governor's time. `vergence interpolate --raw WxH` (no `--fields`) runs the same interpolator and guard on mono frames on a Mac and prints the guard's GPU time; `--no-guard` gives VideoToolbox's frames as they come.
- **60 → 120 (flat 2D, 2026-11-04):** VideoToolbox can't make an in-between frame every 16.7 ms, so `InterpolatingFrameSource` takes rate tiers and `NativeMetalVideoPlayerView` passes `engine:` from Settings → Videos → 2D Interpolator (`AppModel.smoothMotionEngine`): **Automatic** = VideoToolbox ≤ 40 fps, `FlowMidFrameInterpolator` 41–61 fps; **Fast (GPU)** = the GPU one for everything, to A/B it on 24–30 fps. The GPU one is AMD-AFMF-style block matching on a luma pyramid (quarter-size full search, half-size refine with sub-pixel fit, 16 px blocks, vector median, per-pixel choice among nearby vectors, plain-blend fallback): ~1.5 ms GPU at 1080p on an M2 Max vs VideoToolbox's ~18. Held-out PSNR on the Bumblebee clips predicting frame i+1 from i, i+2 (12 fps-equivalent motion, a stress test): within 0.5 dB of VideoToolbox on pans, ahead on the car interior, 2–3 dB behind on the handheld and fight shots, where it ghosts fast edges (blend fallback) rather than smearing. An 8 px full-size level scored worse (matches grain) and was dropped; its constants each moved PSNR < 0.1 dB. The player states 120 Hz and draws at 120 once the display criteria know the doubled rate (`doubledDrawRate`). AI 3D stays VideoToolbox ≤ 40 fps. **Device-unverified:** whether visionOS gives a window 120 Hz; read `presenter … frames/s shown over … draws/s` (5 s, Vergence log) and `interp …` on the M5. `vergence interpolate --raw WxH --gpu [--scale S]` runs it on a Mac.
- **The presenter takes a frame half a draw tick early** (`InterpolatedFramePresenter.earlyAllowance`): at 120 fps on a 120 Hz loop each frame lasts one tick, and a tick landing a hair early used to find two frames due on the next tick and drop one (a deterministic hitch every ~250 ms in the test).
- **Not interpolated:** packed stereo without a track, WebKit playback, a film's own 2D layer, anything above 1080p or 61 fps (40 fps in AI 3D).
- Log lines: `interp …` every 5 s (source fps, minimum reserve, governor state, made/passed/skip reasons, timings) and `frame interpolation paused/resumed/off …`.
